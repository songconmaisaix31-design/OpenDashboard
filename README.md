# OpenDashboard

> 面向单机开发者的本地电脑控制台：在一个界面中查看本机开发服务、理解故障证据、审批有限操作并验证结果。

OpenDashboard 的长期目标不是远程运维平台，也不是任意命令执行器。它聚焦一台开发电脑，把分散在服务状态、API 故障、资源信息、操作审批和审计记录中的上下文汇总到一个本地优先的控制台中。

## 当前真实状态

当前仓库包含一个可运行的简体中文竞赛演示，而不是已经接管本机的完整控制台。

| 能力 | 当前状态 | 说明 |
|---|---|---|
| 中文 Web 界面 | 已实现 | React 19、TypeScript、Vite |
| 故障到恢复五阶段流程 | 已实现 | 确定性内存状态机 |
| 证据、审批、验证和报告 | 已实现 | Fixture 数据，带可见来源与限制 |
| 自动化测试和生产构建 | 已验证 | 以 `npm run check` 为准 |
| 90 秒中文演示视频 | 已完成 | 本地导出，记录于发布报告 |
| 本机状态读取 | 未实现 | 尚未读取真实进程、端口或硬件状态 |
| 本地服务健康检查 | 未实现 | 尚未连接真实 loopback 服务 |
| 真实进程控制 | 未实现 | 当前按钮只确认模拟操作，没有宿主机副作用 |
| Cordis、LocalOps、AUM、Radar、Orca、AgentTeams | 仅规划或 Mock | 不能描述为已集成插件 |

因此，“T0-T10 已完成”只表示阶段交付物已经形成：T0-T4 组成了可运行的 Fixture 演示，T5-T10 是独立规划成果，不是六个已集成运行模块。

## 产品定位

OpenDashboard 服务于在一台电脑上同时运行多个 API、AI Agent 或本地开发服务的开发者。它要缩短这条路径：

```text
看见异常
  -> 查看脱敏证据
  -> 理解当前判断及其限制
  -> 审批一个预定义、有限的操作
  -> 验证结果
  -> 导出按序审计记录
```

首个真实版本采用“只读优先”策略：先证明能安全、准确地呈现本机粗粒度状态，再增加显式注册的 loopback 健康检查。任何真实操作都必须经过单独安全评审，不沿用 Fixture 的恢复结论。

## 明确边界

- 不提供任意 Shell、PowerShell 或用户输入命令执行。
- 不做远程主机、云资源、企业设备或多租户控制面。
- 不读取 `.env`、凭据存储、完整命令行、原始请求正文或授权头。
- 不按 PID 或端口号直接终止未知进程。
- 不把自动端口扫描、插件运行时、工作流编辑器或多智能体协同写成当前能力。
- 不把 Fixture、Mock 或规划数据显示为真实本机观测。

## 本地运行当前演示

要求 Node.js `>=22.12.0` 和 npm `11.x`：

```powershell
npm ci --ignore-scripts --no-audit --no-fund
npm run check
npm run dev -- --host 127.0.0.1
```

当前运行时不会连接真实 provider，也不会控制真实进程。
